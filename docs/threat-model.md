# Threat Model — Payment Gateway for Redsys & WooCommerce Lite

> Produced during adoption (2026-08-01) from `references/security/wordpress.md` and a reading of the real code (no re-run of dynamic tests). Every control below carries its HONEST delivery state — only `IN PLACE` is written in the present tense.

## Assumptions
- Runs inside a WordPress + WooCommerce install the site owner administers; a compromised WordPress admin account can already execute arbitrary PHP and is out of scope for plugin-level defenses.
- Redsys (and Inespay) are trusted external payment processors reached over HTTPS; the plugin does not control their infrastructure.
- The merchant's Redsys SHA-256 secret is entered by the site owner into the gateway's WooCommerce settings and stored as a WordPress option — never committed to the repository (verified during adoption inventory: no secret-shaped strings found in the codebase).
- This plugin handles no card data directly (redirection-based flow to Redsys's own hosted payment page) — PCI scope for card data stays with Redsys, not this plugin.

## Defended controls

| Control | Delivery state | Evidence / where |
|---|---|---|
| Notification signature verification (HMAC_SHA256_V1) before trusting any Redsys/Inespay notification | `IN PLACE` | `includes/class-redsysliteapi.php` (`create_merchant_signature_notif`), invoked from each gateway's `check_ipn_response`/`handle_callback` handler |
| Fail closed when no SHA-256 secret is configured (reject rather than trust an unauthenticated notification) | `IN PLACE` for `class-wc-gateway-redsys.php`, `class-wc-gateway-bizum-redsys.php`, and (fixed 2026-08-01, D-020) `class-wc-gateway-googlepay-redirection-redsys.php` | `classes/class-wc-gateway-redsys.php` ~lines 868–943, **automated-test-verified 2026-08-01** (`tests/Integration/GatewayRedsysIpnTest.php`); `classes/class-wc-gateway-bizum-redsys.php`, same shape, **automated-test-verified 2026-08-01** (`tests/Integration/GatewayBizumIpnTest.php`); `classes/class-wc-gateway-googlepay-redirection-redsys.php`, fixed and **regression-tested 2026-08-01** (`tests/Integration/GatewayGooglePayIpnTest.php` — see "Known vulnerabilities" below for what this replaced); confirmed by the 7.0.1/7.0.2 `readme.txt` changelog entries describing this exact hardening for the original two; also **driven-verified 2026-08-01** in the wp-env playground for the `redsys` gateway — two fabricated POSTs to `?wc-api=WC_Gateway_redsys` with no configured secret were rejected and the target order stayed `wc-pending`, see `docs/playground.md`. `class-wc-gateway-inespay-redsys.php` uses a different mechanism (`hash_equals()`-based HMAC comparison in `handle_callback()`) and already fails closed on a missing signature/API key — not yet automated-test-verified. |
| Order-amount cross-check against the notification total before marking an order paid | `IN PLACE` | `classes/class-wc-gateway-redsys.php` ~line 1026 (mismatch → `on-hold`, never silently trusted) |
| Text domain / i18n consistency (no obvious string-injection surface via translations) | `IN PLACE` | sampled `class-wc-gateway-redsys.php`, consistent `__()`/`_e()` usage with escaping functions (`esc_html__`, `esc_html_e`) present in the sample |
| No secrets committed to the repository | `IN PLACE` | verified during adoption's confidential-data scan (no `.env`, no literal keys found; SHA-256 secret is a runtime WooCommerce option) |
| WooCommerce Settings API used for all gateway configuration (no custom unauthenticated admin endpoints) | `IN PLACE` | all four gateway classes extend `WC_Payment_Gateway` and use `init_form_fields()` |
| CSRF/nonce protection on admin settings forms | `VERIFY` | WooCommerce's Settings API handles this by default for standard fields; not independently re-verified against this plugin's specific field types during adoption (read-only pass) |
| Output escaping across all admin/checkout-rendered strings | `VERIFY` | spot-checked in the main gateway class only; the full tree was not exhaustively scanned for every `echo`/`printf` — flagged as a gap-audit item (see `docs/04-adoption-audit.md`, Security dimension) |
| Capability checks on settings pages beyond WooCommerce's own gating | `VERIFY` | relies on WooCommerce's default `manage_woocommerce` gating for its Settings API pages; not independently re-verified for this plugin |
| Rate limiting / replay protection on the notification endpoint (`?wc-api=WC_Gateway_<id>`) | `TO BUILD` or `MANUAL` (undetermined) | no rate limiting or nonce/replay-window logic observed in the notification handlers beyond signature verification — a valid, correctly-signed notification could in principle be replayed; not confirmed whether Redsys's own protocol prevents this at their end |
| Automated dependency/CVE scanning (`composer audit`/`npm audit`) | `TO BUILD` | no CI, no `composer.json` (no PHP deps to scan); `npm audit` has never been run against `package.json`'s devDependencies as part of this project's process |
| Automated security test coverage (signature verification, fail-closed paths) | `TO BUILD` | no test suite exists at all (confirmed in `docs/03-technical-plan.md`) |

## Known vulnerabilities (found and FIXED 2026-08-01)

| Vulnerability | Where | Impact | Status |
|---|---|---|---|
| **Signature verification bypass via the public merchant code, when no SHA-256 secret is configured** | `classes/class-wc-gateway-googlepay-redirection-redsys.php`, `check_ipn_request_is_valid()` (previously the `else` branch that ran when `$usesecretsha256` was empty) | Unlike `class-wc-gateway-redsys.php` and `class-wc-gateway-bizum-redsys.php` (which explicitly fail closed in this case — see the code comment "No SHA256 secret configured: fail closed... never the non-secret Ds_MerchantCode (FUC)" in both), the Google Pay gateway instead accepted the notification if the decoded `Ds_MerchantCode` in the (attacker-supplied) `Ds_MerchantParameters` equalled `$this->customer` — the merchant's FUC/`DS_MERCHANT_MERCHANTCODE`. That value is **not a secret**: it is sent in plaintext in every outgoing payment form this plugin generates (`set_parameter( 'DS_MERCHANT_MERCHANTCODE', ... )`), so it was trivially readable by anyone who started a checkout. A site that left the SHA-256 secret field empty for this gateway could have a fake "payment successful" notification forged for any order, without any valid signature. Found while reading the full method to write its integration tests (the same pattern used for Redsys/Bizum). | **FIXED 2026-08-01 (D-020, `docs/decisions.md`).** Escalated to the user first, per Keel protocol ("something looks like a security problem → escalate, never patch quietly"); user chose to fix immediately rather than patch quietly. The method now fails closed exactly like Redsys/Bizum. Regression-tested: `tests/Integration/GatewayGooglePayIpnTest.php::test_rejects_the_notification_when_no_secret_is_configured` was confirmed to fail against the pre-fix code (reverted temporarily, confirmed the failure, restored the fix). **Not yet released** — this fix is on `develop`, unreleased; consider it for the next version bump before other work ships alongside it. |
| **`successful_request()` re-verified against the wrong (live-mode-only) secret in Bizum and GooglePay** | `class-wc-gateway-bizum-redsys.php` / `class-wc-gateway-googlepay-redirection-redsys.php`, `successful_request()` | Not an authentication bypass — the opposite failure mode: a genuinely valid, correctly-signed test-mode (or per-order-override) notification would fail this second, redundant verification and the order would silently never be marked paid. Found during the full-plugin review requested by the user 2026-08-01. | **FIXED 2026-08-01 (D-023, `docs/decisions.md`).** Both methods now call the same `resolve_notification_secret()` as `check_ipn_request_is_valid()`. Regression-tested per gateway (confirmed to fail against the pre-fix code, restored, confirmed passing). **Not yet released.** |
| **The actual Redsys signing secret is persisted in plaintext, permanently, to order postmeta** | `class-wc-gateway-bizum-redsys.php:1359`, `class-wc-gateway-googlepay-redirection-redsys.php:~1141` — the `_redsys_secretsha256` meta key | The merchant's real HMAC-SHA256 signing secret — the sole authentication mechanism for the notification endpoint — is written unencrypted to `wp_postmeta` and never expires. Anything with order-meta read access (another plugin, a GDPR/data export tool, DB access, an export feature, support staff) can read it. If it matches the currently-active merchant secret, that's a full compromise of future notification authenticity for that gateway. Found during the full-plugin review requested by the user 2026-08-01. | **Documented, NOT fixed (D-025, `docs/decisions.md`).** This meta write is load-bearing for the per-user test-mode feature (`testforuser`/`testforuserid`): it lets a delayed notification (arriving after the 1h order-number-mapping transient expires — e.g. a refund confirmation) still be verified with the secret that was actually used to sign that specific order. Removing it without a replacement could silently break that path for real merchants using the feature. User was offered three options (stop persisting + accept the residual risk / encrypt before storing / leave documented) and chose to leave it documented and decide later, rather than have a fix guessed at. |

### Found and FIXED (full-plugin review, 2026-08-01 — see D-024/D-026 in `docs/decisions.md`)
All 7 lower-severity findings from the review were fixed at the user's request, in the same session as D-025's deferral:

| Finding | Where | Severity | Status |
|---|---|---|---|
| Unauthenticated blocking `sleep(5)` on the order-received page, before any signature check | `woocommerce-redsys.php:385` | Medium — repeatable resource-exhaustion vector for anyone with (or who leaks) a valid order key; also delays every legitimate customer's page load by 5s | **FIXED (D-026).** 30-second per-order rate-limit transient + an already-paid order exits before the sleep. Regression-tested (`tests/Integration/MarkOrderAsPaidRateLimitTest.php`, times actual calls, confirmed to fail against the pre-fix code). |
| Real order lookup happens BEFORE signature verification | `class-wc-gateway-bizum-redsys.php` / `class-wc-gateway-googlepay-redirection-redsys.php`, `resolve_notification_secret()` | Medium — unauthenticated order-existence probing / possible uncaught-exception 500 | **FIXED (D-026).** The order lookup is now wrapped in try/catch, falling back to the guest/no-user secret instead of letting the exception surface as a 500. Regression-tested per gateway. |
| Order-number-mapping fallback can resolve the wrong order after the 1h transient expires | `class-wc-gateway-redsys-global-lite.php:1085-1105` | Medium/correctness — `wp_rand(1,999)` produces a 1–3 digit prefix, but the fallback always strips exactly 3 characters | **FIXED (D-026).** `wp_rand(100,999)` guarantees the prefix is always 3 digits. Regression-tested (`tests/Integration/GlobalLiteOrderNumberTest.php`, confirmed to fail against the pre-fix code across 3 separate runs). |
| Non-constant-time signature comparison (`===`/`!==` instead of `hash_equals()`) | All HMAC gateways except Inespay | Low — theoretical timing side-channel | **FIXED (D-026).** All 6 comparison sites now use `hash_equals()`. Existing accept/reject tests confirm behavior is unchanged for both outcomes. |
| Refund-confirmation callbacks can land in the "payment completed" branch | `class-wc-gateway-inespay-redsys.php`, `handle_callback()` | Low-medium — misleading note/meta/hook; not exploitable to un-refund (WooCommerce's own guard blocks that) | **FIXED (D-026).** A `! $order->needs_payment()` guard treats an OK/SETTLED callback for an already-resolved order as informational only. Regression-tested, confirmed to fail against the pre-fix code. |
| Cart total truncated to `(int)` before comparing to the transaction limit | `class-wc-gateway-inespay-redsys.php:201` | Low — a fractional cart total can incorrectly pass the limit | **FIXED (D-026)**, compares as floats now. Verified by code review + `php -l` only — not independently regression-tested (`is_checkout()`/`WC()->cart` context isn't straightforward to fake in `WP_UnitTestCase` without disproportionate scaffolding for a one-line fix). |
| An explicit `0` refund amount is treated as "not given" | `class-wc-gateway-inespay-redsys.php:652` | Low — refunds the full order total instead of nothing | **FIXED (D-026).** Checks `null !== $amount` instead of a falsy check. Regression-tested (mocks `pre_http_request`, captures the actual API payload sent), confirmed to fail against the pre-fix code. |

## Not defended
| Not defended | Consequence | If you need it |
|---|---|---|
| A compromised or malicious site administrator | Can already execute PHP; no plugin-level control survives that | Nothing at the plugin level — hosting/account security |
| Other plugins and the active theme | Share the process, database and global scope; a hostile or broken one can alter this plugin's behavior | Defensive prefixing (already used: `redsys`/`bizumredsys`/etc. IDs), capability re-checks at each entry point |
| Data at rest in the database | The SHA-256 secret and other settings are stored as WordPress options, unencrypted, as the platform provides | Encrypt the specific field before storing and own key handling — not currently done, not currently required by the plugin's threat profile (a compromised DB with admin access already exposes more) |
| Brute force against `wp-login` and the WooCommerce REST API | Out of this plugin's scope | A dedicated security plugin, host-level rate limiting, or a WAF |
| Replay of a validly-signed Redsys/Inespay notification within its (unknown) validity window | Same order could in principle be re-processed if Redsys's own protocol doesn't prevent it | Would need explicit replay protection (nonce/timestamp tracking) at the plugin level if Redsys doesn't guarantee it — flagged as `TO BUILD or MANUAL (undetermined)` above, worth clarifying with Redsys's own protocol documentation before building anything |
| Supply chain of build-time devDependencies (`@wordpress/scripts`, webpack, etc.) beyond a manual read | `npm audit` has not been run as part of this project's process | Run `npm audit`, review advisories, pin versions |
| PII in debug/error logs | This plugin has no dedicated debug-log-with-a-switch (Keel's own contract) yet | Add one per Keel's debug-logging contract when Phase 5 scaffold work happens; redact at the log call |
